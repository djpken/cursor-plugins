### Autopilot-full

**你擁有判定，而非 PR。每個 PR 由一位負責人從建置到合入全程負責，且在你群組（未曾撰寫該程式碼）證明即將合入的程式碼之前，任何內容都不會合入。**

一個判定涵蓋一個變更集，而綠色 CI 涵蓋一個最新版本。步驟 4 執行一次完整群組驗證，且僅在重大變更時再次執行。`playbooks/shipping.md` 中的 patch-id 規則可攜帶一個通道的結果，且每個新的最新版本都需要自己的綠色 CI。

1. **操作者的門禁優先。**授權僅涵蓋佇列中的專案，因此操作者指定為其所有的專案以及不在佇列中的 PR 會在合入準備階段停止。要求陳述計畫並非開始指令。
2. **每個 PR 指派一位負責人，並將其工作儲存在可被替代者找到之處。**為整個程式一次解決 forge 問題。GitHub CLI（`gh`）是預設。若 `command -v origin` 成功且 Origin 能解析儲存庫，則對每個 PR 操作使用 `origin pr`。否則維持 `gh` 並記錄此替代方案。絕不要求 Graphite（`gt`）。每位負責人是一個 Cursor 雲端代理，負責建置、依照 `playbooks/opening-a-pr.md` 開啟其 PR、在真實成品上證明變更、依照 `playbooks/babysit.md` 監護至綠色狀態，並在步驟 4 和 5 清除後合入。

   及早開啟 PR，讓 CI 和 bots 與工作同時執行。程式碼僅在 slop-strip（來自 `cursor-team-kit` 外掛（`/deslop`）的 `deslop` 技能）和 `/no-comments` 檢查之後才算完成，因此完整群組驗證執行於完成的程式碼上。然後重新基底到當前主幹，並在自我證明之前報告程式碼完成的最新版本，以便驗證執行於變更將合入的基底上。報告每個後續的最新版本，並在自我證明、CI 和監護完成後報告合入準備狀態。修復回合維持在同一基底，除非主幹衝突或破壞 CI，因為每次重新基底都會重新啟動 CI。在程式碼完成推送之前以及需要驗證者的後續推送之前，在已提交的最新版本上執行儲存庫對受影響路徑的檢查。

   假定 VM 會死亡。開始後不久，依照 **show-me-your-work** 技能，在根代理的儲存庫（路徑在系統提示中）中推送並啟動決策記錄，然後在每個值得保留的單位後推送。任何指派子代理的人記錄其 id、狀態以及過去類似執行中該類代理的 stuck-after 執行時間於該儲存庫中，以便根代理在父代理死亡時可探查它。僅強制推送你自己的分支，將 `--force-with-lease` 固定到你最後推送或接管時的 SHA，且在任何不是你做的推送上，停止並報告給根代理。
3. **負責人從主幹平行執行，絕不堆疊，**以便每個 PR 獨立合入。
4. **群組驗證一次。**完整群組驗證執行一次，於程式碼完成的最新版本。另一完整群組驗證僅針對新行為、重新設計或大型新變更集。重新基底、合入衝突解決或小修復僅需一個驗證者於新最新版本。依照 **swarm** 技能，在程式碼完成的 SHA 上分散獨立驗證者。他們重新執行門禁，透過其控制技能（如 `control-ui` 或 `control-cli` 來自 `cursor-team-kit`）或指定的驅動器，在真實表面上證明關鍵行為，並審核變更集。若沒有真實通道或未審核合入準備報告的收據，判定不算乾淨，因為每個通道不會信任未檢查的宣告。

   將每個已證明的發現（無論通道標記為何）以一次修復前送給負責人，並在每個具有相同缺陷的網站上放置紅色測試。主幹上顯示但不在 PR 中的缺陷記錄於主幹且不阻擋 PR，但 PR 複製或新達及的缺陷是 PR 自身的。絕不自行推送修復，因為每個分支只有一位寫者。應取代停滯的負責人。
5. **負責人僅合入你已驗證、且在其合入主幹上測試過的內容。**綠色 CI 單獨絕不允許合入。一旦群組通道已開始，合入準備會重新基底到當前主幹，報告新最新版本，並等待綠色 CI。

   緊接合入之前，取得主幹並詢問其變更是否可能影響變更集，因為每次主幹移動都重新基底永無止境。當即將合入的程式碼未曾測試時，如衝突、雙方都變更的檔案或 PR 檢查的變更，則重新基底並等待 CI。雙方都變更的 lockfile 不需重新基底，當凍結安裝在合入結果上成功且 PR 變更的套件在該處如同在最新版本上可解析，因為該安裝測試即將合入的 lockfile，且失敗的安裝意味重新基底必須修復它。當主幹變更了變更集的呼叫者或變更集所依賴的內容，如其所呼叫的程式碼或依賴版本，則在合入結果上執行變更集的檢查並在成功時合入。否則合入。若主幹會迫使超過合入準備的第三次重新基底，則暫停並報告給根代理，其會排序衝突的工作。
6. **執行根層。**任何鬆綁門禁的事物，如提高的預算或 allowlist 專案，需要驗證者的證明然後你的新簽章，因為負責人是想要綠色的一方。在涵蓋核准的授權下，該簽章是核准，且負責人對其記錄指向你的簽章以供通道檢查。禁用或軟失敗的檢查總是會出現，因為它停止保護每個案例。絕不給予或繞過 forge 強制的核準，因為任何簽章都不涵蓋它。

   在操作者的開始指令下，武裝 `/loop 1h` 審核直到沒有委派工作剩餘，因為長時間執行會漂移且代理會靜默停滯。每個 tick 從主幹重新讀取此 playbook 並修正漂移，如未報告的最新版本或未記錄的代理，由其負責人記錄它，因為漂移是記錄中的缺口，而非停滯。它探查每個代理，直到葉通道，並根據其副作用判斷每個代理，因為狀態文字和摘要可隱藏停滯的子代理。代理在錯誤、無法開始回合或超過其 stuck-after 執行時間後無新內容時是停滯，且負責人在第一個 tick 之前未推送或寫入記錄行也是如此。等待你或操作者的代理不是停滯，因此回答它。立即取代停滯代理，不等待其停止生效。一個 tick 為操作者改變了事物時，依照 **ketchup** 技能結束於讓操作者跟上，而一個未改變事物的 tick 保持安靜。
7. **在操作者的停止指令下立即停止。**暫停作為零寫入命令到達每個負責人。每個負責人報告其位置並保持其任務簡報直到操作者釋放它。

**回覆：** 依照 **ketchup** 技能向操作者更新狀態，涵蓋每個 PR 的狀態與結論、已合入的內容、簽核與原因，以及開放的操作者門控，並附上每個 PR 與相關軌跡的連結。
