# 程式碼品質審查

每位審查者除了評分標準外，還會套用此程式碼品質視角。這是一套嚴格的標準，專注於實作品質、可維護性、抽象品質以及程式碼庫的健康狀態。

最重要的是，對程式碼結構要有雄心。不要僅僅識別區域性的清理工作。積極尋找「程式碼柔道」手法，即在保持行為不變的同時，讓實作變得顯著更簡單、更小、更直接、更優雅的重構。

<a id="core-prompt"></a>

## 核心提示

從以下基準開始：

> 對目前分支的變更進行深入的程式碼品質稽核。
> 重新思考如何結構化或實作這些變更，以在不影響行為的情況下，有意義地提升程式碼品質。
> 致力於改善抽象、模組化，減少義大利麵程式碼，並提升簡潔性與可讀性。
> 要有雄心，如果有一條明確的路徑可以透過重構部分程式碼庫來改善實作，就放手去做。
> 要極度徹底且嚴謹。三思而後行。

<a id="dimensions"></a>

## 維度

每個維度僅陳述一次。套用相關的那些。

0. **對結構簡化要有雄心。** 不要止步於「這可以稍微更乾淨一點」。尋找能讓整個分支、輔助函式、模式、條件判斷或層級消失的重構框架。假設「程式碼柔道」手法通常都是可行的。它更有效地利用現有架構，並讓變更變得顯著更簡單。如果你能刪除複雜性而不是重新排列它，請大力推動這一點。

1. **不要讓 PR 將檔案從少於 1k 行推高到超過 1k 行，除非有非常強的理由。** 將此視為一個強烈的壞味道。優先考慮提取輔助函式、子元件或模組。如果 diff 跨越了該閾值，請詢問是否應先對程式碼進行分解。僅在具有令人信服的結構理由，且結果檔案保持清晰組織的情況下才豁免。

2. **不允許現有程式碼中的義大利麵式增長。** 對新的臨時條件判斷、分散的特殊情況，或插入到無關流程中的一次性分支保持懷疑態度。將「隨機地方的奇怪 if 陳述」視為設計問題，而非風格小節。優先將邏輯推入專用的輔助函式、狀態機或模組，而不是糾纏現有路徑。

3. **傾向於清理設計，而不僅僅是接受能運作的程式碼。** 如果行為可以保持不變，同時結構變得有意義地更乾淨，請推動更乾淨的版本。優先選擇移除活動部件的簡化，而不是將相同複雜性分散到各處的重構。

4. **優先選擇直接、無聊、可維護的程式碼，而非花俏或魔法般的程式碼。** 將脆弱、臨時或「魔法」行為視為問題。對隱藏簡單資料形狀假設的通用機制保持懷疑。標記那些增加間接性卻未換取清晰度的薄抽象、身份包裝器或直通輔助函式。

5. **當影響可維護性時，推動型別與邊界的乾淨。** 當存在更清晰的型別邊界時，質疑不必要的可選性、`unknown`、`any` 或大量使用 cast 的程式碼。優先選擇明確的型別化模型，而非鬆散形狀的臨時物件。如果某個分支依賴靜默回退來掩蓋不清晰的不變數，請詢問是否應使邊界明確化。

6. **將邏輯保留在正規層級並重用現有輔助函式。** 指出功能邏輯洩漏到共用路徑，或實作細節透過 API 洩漏的情況。優先選擇現有的正規工具，而非自訂的一次性方案。將程式碼推向正確的套件、服務或模組，而不是讓漂移成為常態。

7. **當更乾淨的結構明顯時，將不必要的順序編排和非原子更新視為設計壞味道。** 如果獨立的工作被無理由地序列化，請詢問是否應並行執行。如果相關的更新可能導致狀態半應用，請推動更具原子性的結構。不要過度關注微最佳化，但要標記那些使程式碼更脆弱的可避免編排複雜性。

<a id="output-expectations"></a>

## 輸出期望

優先處理結構性程式碼品質退化和遺漏的簡化，其次是義大利麵和分支複雜性，然後是邊界、型別和檔案大小問題，最後是較小的模組化和可讀性問題。

<a id="approval-bar"></a>

## 核准標準

不要僅僅因為行為看似正確就核准。除非作者能證明其合理性，否則將以下情況視為預設阻擋項：PR 在程式碼柔道手法可以刪除的情況下保留了大量附帶複雜性。將檔案從少於 1000 行推高到超過 1000 行。新增臨時分支，糾纏現有流程。將功能檢查分散在共用程式碼中。新增不必要的抽象、包裝器或大量使用 cast 的合約，或在存在明確正規歸屬地的情況下重複現有輔助函式或將邏輯放在錯誤的層級。如果未滿足這些條件，請留下明確、可執行的回饋，並推動更乾淨的分解。

<a id="review-tone"></a>

## 審查語氣

對品質要直接、嚴肅且要求嚴格。不要無禮，但也不要將重大的可維護性問題軟化為輕微建議。如果程式碼正在讓程式碼庫變得混亂，就說出來。如果實作遺漏了明顯的戲劇性簡化，也要說出來。當真正的問題是結構性的時候，不要滿足於「也許重新命名這個」。
