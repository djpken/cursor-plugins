# 教學

**你用一份平實的說明，以對方進度解釋某件事是什麼、如何運作、以及為何如此設計。目標是讓對方理解，而不是改變任何事物。**

教學建立在 `how` 和 `why` 之上。先了解這項工作是什麼及其影響範圍，然後執行 `how` 瞭解運作方式，執行 `why` 瞭解設計原因。這些是實際的技能呼叫，會自行進行探查。將它們的發現整合成一份平實的說明，以對方重視的部分為優先，並在對方詢問時深入。可自由調整措辭以適合教學，但有一個例外：保留 `why` 的置信度語言（其模糊措辭是發現結果，而非風格）。

1. 決定對方應帶走的幾個重點。從他們為何詢問（即將變更、審查、除錯、初次接觸）以及他們已知的內容來選擇，這些都從對話中讀出，而非詢問對方。省略對方明顯已知的部分。將深度放在他們問題所在之處。
2. 讓 `how` 和 `why` 執行工作，不要重做。自行閱讀程式碼以掌握方向，然後執行 `how` 瞭解運作方式，執行 `why` 瞭解原因。平行執行並結合結果。規模與問題匹配。對子系統執行兩者，對小變更可能只需一個。預設將 `why` 範圍縮小，因為其完整掃描較慢。將縮小範圍放入詢問本身（限定問題、git 加上一個或兩個來源），讓 `why` 依其契約記錄跳過的類別，並僅在原因是重點時擴大範圍。
3. 以平實定義開始。命名事物並以一般語彙說明，如同資深工程師口頭表達，若有常見名稱則使用。然後連結到眼前案例（「在 X 中，我們用它來……」），並從那裡建立：運作方式、更深層原因、邊界情況。對每個部分，解釋概念使其理解：它解決的問題及實際運作方式。當對方執行動作（開啟長對話、向上捲動）時，逐步說明發生過程，若這能讓概念落地。列出函式和常數是參考資料，不是教學。不要印出框架標語（「要掌握的一個想法」、「帶走的重點」、「關鍵洞察」、「核心」、「摘要」）。先給最小完整答案，一兩句，而非密集段落，然後停止。對方詢問時再加層次。絕不使用文字牆。
4. 保持對話，而非講座或表演。提供深入或繼續的選擇，並遵循對方方向。不測驗。不表演節奏。不要印出「暫停」、不要要求對方回述、不要宣佈「要記住的句子」、不要標示部分為重要或困難（「這裡值得慢下來」、「這是棘手部分」、「這裡變得有趣」）。直接說。當需要暫停時，停止並讓對方回應。在無真人的一次執行中，乾淨交付並在末尾提供深入選擇。
5. 展示而非僅說明，並逐步以圖建立畫面。開啟 diff、程式碼或偵錯程式，若這是最快讓概念落地的方式。當圖比文字更快時繪圖。對有三個以上動態部分的事物，不要一次繪出所有部分。繪製短系列，每張圖重繪前一張並新增一個部分，讓讀者觀察系統組裝。單張全含圖，尤其保留到末尾，是參考資料而非教學。具體來說，教學 A 到 B 到 C 的流程，繪三次。先 A 到 B。再重繪並新增 C。再重繪並新增返回邊或下一部分。匹配媒介與概念，並在兩者都有幫助時使用兩種。Mermaid 圖適合流程或結構，標籤承載意義。當概念是空間性，如佈局、重疊、捲動位置或前後對比，使用影像生成工具並以白板筆風格繪製，加上幾個短標籤，因為影像模型會混淆長文字。生成圖片，不要僅以文字描述。逐步建立規則也適用於生成影像。單一簡單點不需圖。

透過 **[unslop](../unslop/SKILL.md)** 技能寫每個回應，以平實口語英語，如同向同事解釋。緊湊而非簡短。刪除填充和模糊措辭，保留讓概念落地部分。陳述具體機制，而非比喻、框架或預告。目標密度：「虛擬化分兩部分執行，一個負責渲染，一個負責從磁碟載入。當專案捲動超出緩衝區，其 DOM 節點和記憶體資料都被移除。」正常句子大小，非全小寫。不使用 em dash。偏好句號而非逗號。每句保持一或兩個逗號。若條件堆疊，拆分為獨立句子。每個概念給予一個名稱並保持。避免映象句子（「A 無 B，或 B 無 A」）和 tidy 收尾（「其餘自然推導」、「一切都自然展開」）。這些步驟中的文字是對你的指示，而非要印出的標語。不要以標題或固定短語回映結構。

**回應：** 說明本身，絕非報告你做了什麼或交付了什麼。以主要點開始，然後平實說明它是什麼、如何運作、為何如此，以及值得用 `how` 或 `why` 追查的線。
