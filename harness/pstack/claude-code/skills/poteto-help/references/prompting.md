# 措辭提示

提示會說明意圖與完成檢查。劇本提供步驟，因此幾句簡單的句子勝過詳細規格。

<a id="put-in"></a>

## 放入

- 目標。說明問題或使用者想要什麼。
- 完成檢查。它可以成功或失敗。「做得更好」和時間長度不是檢查。
- 要展示的證明。要求真實的指令輸出、流程影片、儲存的值，或前後數字。
- 使用者已知的資訊。症狀、重現步驟、記錄或連結可省去代理的搜尋。
- 真實的限制。「先重現」、「不要更改任何程式碼」、「零行為變更」和「讓我先審閱再繼續」都會改變代理的動作。

<a id="leave-out"></a>

## 省略

- 做法。說明要達成什麼，並留給代理空間尋找更好的方式。
- 技能或步驟列表。手寫的順序會刪除或重新排列劇本保留的步驟。僅在要覆蓋一個選擇時命名技能。
- 使用者對原因的理論，直到代理重新表述問題。已陳述的猜測會縮窄搜尋範圍。

<a id="load-the-context-first"></a>

## 先載入上下文

- 對於雜亂的報告，要求代理先用自己的話和簡單英文重新表述核心問題，再做任何其他事情。誤讀會在任何程式碼存在之前出現。
- 在新對話中，`/recall` 先前主題的工作。舊對話擁有新代理缺乏的上下文。
- 在更改陌生程式碼之前，要求 `/how` 提供機制和 `/why` 提供原因。沒有追蹤模型的代理會在第一個看似合理的位置修復症狀。
- 要求 `/teach` 為選擇提出理由，例如「說服我它修復原因而非症狀」。理由比摘要更容易檢查。

<a id="design-before-the-plan"></a>

## 先設計再規劃

- 絕不接受第一個設計。要求幾個選項的原型，對 UI 提供截圖或影片，並從證據中選擇。
- 讓原型回答開放問題。不要對抽象計劃進行敵意審閱，因為審閱者會發想不會發生風險。
- 對於共享包或 API，先要求 README 或教程，然後回溯到程式碼。該文件成為代理自我檢查的目標。
- 僅在設計確定後要求計劃。每個計劃步驟以檢查結束。

<a id="follow-up-short"></a>

## 簡短地跟進

- 「執行」、「繼續」和「持續直到完成」是完整提示，一旦對話包含任務。
- 當主題變更時，以「新任務」開始。否則模式會將訊息視為下一步。

<a id="before-stepping-away"></a>

## 離開之前

- 說「我要睡覺」或「我要離開」，讓代理停止詢問。
- 將完成寫成每次迭代可執行的檢查，並給 `/loop` 該預測。
- 要求從命名基底建立新的工作樹。
- 預先回答代理會停下詢問的事，例如「不要在提交前問我」。
- 要求決策紀錄以便後續審閱。
- 提供退出：「如果幾小時後你真的陷入困境，停止並寫下原因」。

<a id="steer-in-one-line"></a>

## 一行引導

- 重新表述目標：「我說目標是重現。我尚未要求修復。」
- 命名原則：「應用證明它可行。顯示真實輸出，而非構建紀錄。」
- 原則名稱有效，因為代理已讀過規則。其回應會命名該規則改變的決策。
