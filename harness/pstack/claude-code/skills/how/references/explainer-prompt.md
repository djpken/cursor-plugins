<a id="instructions"></a>

## 指示

每個探索代理都調查了同一子系統的不同面向。他們的發現結果在某些地方會重疊，偶爾也可能相互矛盾。請加以協調。合併重疊的描述，透過自行檢查程式碼來解決矛盾，並將這些獨立的片段整合為統一的整體圖景。

撰寫一份說明，讓不熟悉此領域的資深工程師閱讀後能建立穩固的心智模型，並對架構有足夠的理解，從而能自信地開始在此領域工作。

您對程式碼庫擁有唯讀存取許可權，可用於檢查任何內容、釐清細節或填補空白。視需要使用 Read、Grep 和 Glob。探索代理已經完成了工作，因此您不應需要從頭開始重新探索。

<a id="output-format"></a>

## 輸出格式

使用此結構，並根據問題的性質進行調整。並非每個問題都需要所有章節。

<a id="overview"></a>

### 概覽
1 至 2 段。這是什麼、它做什麼、為什麼存在。讀者應能僅憑此部分決定是否繼續閱讀。

<a id="key-concepts"></a>

### 關鍵概念
理解後續內容所需的重要型別、服務或抽象。提供簡短定義，無需詳盡無遺。

<a id="how-it-works"></a>

### 運作方式
這是說明的核心，也是最長的章節。逐步說明流程：觸發條件、逐步發生的事件、資料流向、決策點。

使用散文而非偽程式碼。引用具體的檔案和函式，讓讀者知道該檢視哪裡，但除非程式碼片段對論點至關重要，否則不要貼上大段程式碼。

當流程涉及多個元件相互通訊，或資料經過多個階段轉換時，請包含圖表。使用 mermaid (```mermaid) 來表示結構化的流程（時序圖、流程圖、元件圖），或使用 ASCII 藝術來表示較簡單的關係，以免 mermaid 過於繁瑣。請自行判斷。圖表應用於澄清，而非裝飾。如果散文已涵蓋流程，則可省略圖表。

<a id="where-things-live"></a>

### 檔案存放位置
簡要的檔案/目錄結構圖。僅列出新進人員開始工作時需要知道的專案。

<a id="gotchas"></a>

### 注意事項
不顯而易見的事物、令人意外的行為、歷史背景、常見陷阱。若沒有值得特別說明之處，請略過此節。

<a id="communication-style"></a>

## 溝通風格

- 使用具體語言，而非抽象概念的抽象描述
- 說「`UserService` 呼叫 `AuthClient.refresh()`」，而不是「服務委派給客戶端」
- 當事物複雜時，說明為何複雜。不要僅描述複雜性
- 當事物簡單時，不要多加冗詞
- 若有有用的比喻，請使用。若沒有，不要勉強湊合
- 若探索者標出開放問題或缺口，請承認它們，而非隱藏
