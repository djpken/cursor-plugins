<a id="maintain-a-verification-skill"></a>

# 維護驗證技能

In Claude Code, read [the Claude Code adapter](../../docs/harness/claude-code.md) once per session before you follow this skill. It maps the Cursor names in pstack skills to Claude Code.

功能圖在應用程式變動時就會失效。此技能是針對 `/create-verification-skill` 產出的技能（或任何具有功能圖的專案本地驗證技能）的維護迴圈。嚴謹的單位是功能，而非每個句子：從來源涵蓋每個功能檔案，並實際操作每個功能，而不需將每個專案都終止化。

<a id="outcomes"></a>

## 結果

選擇一個，並說明選擇原因：

- **clean**。每個功能都有來源與例項覆蓋；沒有值得發布的內容。沒有分支，沒有 PR。
- **changed**。一個 PR 發布經過驗證的檔案、測試框架或地圖修正。
- **blocked**。覆蓋無法完成，或經過驗證的修正無法安全發布。請明確說明阻擋原因。

<a id="edit-scope"></a>

## 編輯範圍

僅編輯驗證技能自身的目錄（其 SKILL.md、features/ 及它所擁有的任何測試工具指令碼）。執行期間絕不編輯產品程式碼：功能圖描述的行為但應用程式不再執行，若非文件漂移（修正功能圖）或產品回歸（報告，而非在文件中掩蓋）。

<a id="pass"></a>

## 流程

0. **定位目標。** 找到要維護的驗證技能：專案本地技能，其主體包含啟動/驅動章節及功能圖（通常為 `.cursor/skills/verify-*/`）。若有多個候選 → 詢問選擇哪個；無 → 停止並指向 `/create-verification-skill`，而非自行建立目標。

1. **索引衛生。** 閱讀功能圖 README 並瀏覽其同級檔案。修正缺失、多餘、重複或失效的條目。輕量處理；不生成清單。

2. **來源掃描。** 每個功能檔案一個只讀子代理，同時啟動。每個子代理從來源解釋「此使用者面向功能如何運作？」，標記可能的文件漂移並附引用，並返回一個簡潔的實際操作驗證配方。子代理絕不驅動應用程式或編輯檔案。返回格式：功能摘要 / 來源入口點 / 可能的漂移或無 / 一個配方。

3. **Reconcile.** 每個功能檔案都有回傳的摘要。將重疊的配方合併為盡可能少的應用程式狀態。抽查引用的漂移；不要重新證明已標記為 clean 的宣告。掃描近期變動，找出地圖中遺漏的使用者介面表層。在判定遺漏之前，必須要求具體的來源路徑。

4. **Live pass.** 即使來源看起來乾淨，也必須執行。協調者負責所有驅動操作；遵循驗證 skill 自身的啟動模型。對於伺服器與 UI，使用一個長生命週期例項進行序列驅動；對於短生命週期 CLI，每次驅動使用新的隔離 session（由 skill 的 Launch 章節決定，而非此處）。至少執行每個功能一次，並在整個過程中保持三個不變數，無論失敗為何：(1) 永遠不要驅動一個自上次出現異常行為以來未進行健康檢查的例項。在首次驅動前執行 doctor，在以 session 為單位時，每個新 session 都執行 doctor，在任何驅動失敗後再次執行 doctor，且當 doctor 無法看到失敗（例如健康程式上的卡住 UI 狀態）時，重置為已知狀態或重新啟動，而不是抱持希望；(2) 迄今收集的證據在每次清理後都必須保留，並在其指定位置進行檢查，而非假設存在；(3) 任何由驅動啟動的內容都不應比該驅動的效用存活更久。無論 session 是卡住、結束還是共享，失敗迭代的殘留物都必須清理（對於共享例項，清理殘留物，而非例項本身）。由 skill 漂移引起的 doctor 失敗屬於漂移：在編輯範圍內修正並重試一次。重新啟動修正所使無效的任何內容，不多不少。然後再將該 pass 標記為 `blocked`。無法到達的功能只有在提供具體先決條件（驗證、許可權、作業系統、外部狀態）與嘗試的路由時，才標記為 `verified-unreachable`；如果地圖遺漏該先決條件，則屬於漂移。任何來自分類的測試框架修正在發布前必須重新進行例項驅動。最終拆除發生在該次執行的最後一次驅動之後。包括那些重新證明。因此沒有任何內容比該次執行存活更久（證據保留，依 skill 規定）。

5. **分類。** 錯誤或缺失使用者觀點描述 → 文件漂移，修正它。可運作行為但測試工具無法驅動 → 測試工具缺口，修正它；測試工具修正遵循與生成相同的輔助規則（指令碼可執行，技能主體中記載呼叫方式）。應用行為實際故障 → 產品缺口；記錄給使用者，不納入此 PR。

6. **提交或停止。** 對於 changed：一個包含已證實修正的 PR，先重新閱讀每個變動檔案。對於 clean 或 blocked：不提交 PR，誠實報告結果與涵蓋情況。

在暫存位置保留簡潔的執行記錄（涵蓋的功能、無法達到的前置條件、確認的漂移、結果）；不提交它們。
